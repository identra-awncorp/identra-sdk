# Identra SDK micro-benchmarks

Plain ESM scripts that import the BUILT packages (`@identra/sdk-core`, `@identra/sdk-core/webcrypto`,
`@identra/sdk-app`). Nothing under `packages/` is touched, no network, no ports, no Docker.

```sh
npm run build                           # once, if packages/*/dist is stale
sh scripts/pki/ensure-test-pki.sh       # once: the DEMO PKI in .pki/demo (git-ignored)
node bench/run.mjs                      # or: npm run bench          (about 5 minutes)
node bench/run.mjs --json               # also writes bench/results.json (git-ignored)
node bench/run.mjs --only=chain         # only the cases whose name or backend contains "chain"
node bench/run.mjs --min-ms=200         # quick smoke run; the numbers are NOT comparable
```

Output: one Markdown table (case, backend, ops/s, mean, p50, p95, p99 in ms, n, run spread), the
environment (CPU, cores, Node, V8, OpenSSL, OS, governor, load average), peak RSS of the whole run,
and the sizes in bytes of an issued diploma, a 2-claim presentation, a status-list token and the
trust-list token (and a 3 KB wallet JWE).

## What is measured

| # | case | backend |
|---|---|---|
| 1 | ES256 sign, verify of a 512-byte message | WebCrypto (`@identra/sdk-core/webcrypto`: server, browser) and noble (`@identra/sdk-app`: phone) |
| 2 | `createCertificateChainValidator(...).validate`, `vc` profile, `[leaf, issuing CA]` to a pinned root, with `expectedIssuerUri` | both |
| 3 | `issueDiploma`: 7 claims, decoy digests, `x5c` header | WebCrypto issuer |
| 4 | `createPresentation`: KB-JWT, discloses 2 of 7 claims | noble holder key and hasher |
| 5 | `verifyPresentation` (structure, chain, signature, trust lookup, status, disclosures, KB-JWT): with an in-memory trust registry and status checker (no I/O); with the REAL `createSignedTrustListRegistry` + `createStatusListChecker` over an in-memory `fetch` that returns real signed tokens, caches warm; and one COLD call (fresh registry and checker: verifies the trust-list token, the status-list token and decodes the list) | both |
| 6 | status list: build (131 072 x 2-bit, 1 311 entries = 1% set, seeded) + `createStatusListToken`; `verifyStatusListToken` + decode | sign: WebCrypto; verify: both |
| 7 | trust list: `createTrustListToken` with 5 organisations (4 issuers + 1 verifier); `verifyTrustListToken` | sign: WebCrypto; verify: both |
| 8 | `verifyProductChain`, 3 events, real lists, warm caches | WebCrypto (browser-like) |
| 9 | `encryptJwe` / `decryptJwe`, ECDH-ES + A256GCM, 3 072-byte payload | noble |

The credential is always issued by the WebCrypto issuer (`truong-mau` `vc` certificate of the DEMO
PKI) and held by a noble key, as in production. The "backend" of a verification case is the
`Verifier` / `Hasher` pair handed to the verifier (and to its chain validator).

## Method

- One process, cases run one after another. Time comes from `process.hrtime.bigint()`, taken around
  every single call (`await fn()`), so p50/p95/p99 are per-call latencies (nearest rank), not batch
  averages. ops/s = n / sum of the call times.
- Warm-up: at least 500 ms and 10 calls before anything is measured (JIT, caches). A short probe then
  sets n so that one run lasts at least 2 s (target 2.3 s; a run shorter than 2 s is discarded and n grown).
- Each case runs 3 times with the same n; the reported run is the median by ops/s. "run spread" is
  (best - worst) / median of the three runs, a noise indicator. `results.json` has all three.
- Sanity: before timing and again after it, every case checks the REAL result. Verifications must
  return `ok === true` (and the expected claims: `ho_ten`, `nganh` visible, `ngay_sinh` not); the
  cases with real lists also assert that the fetch call count did not grow, i.e. the caches stayed warm
  and no timed call included a refetch. Sign/verify check a verification of the produced signature and
  that a verify of other data is `false`. A failed assertion aborts the run.
- Time is pinned: `now` / the clock is one hour after the newest DEMO certificate's `notBefore`, so
  all tokens and caches stay valid however long the run takes. The DEMO PKI is regenerated by
  `ensure-test-pki.sh`, so the exact certificate bytes (and sizes) change between machines.
- The cold row is the median of three fresh registry + checker instances, one call each (n = 1). The
  code is already JIT-warm (the earlier cases ran), only the LIST caches are cold: it is not a
  "first call after process start" number.
- Peak RSS is `process.resourceUsage().maxRSS` at the end of the whole run.
- Nothing is pinned to a CPU core, no `--expose-gc`: garbage collection pauses are inside the numbers
  (they show up in p95/p99). The machine is whatever it is at the time; the load average is recorded.

## Caveats

- V8 on a desktop CPU is NOT a phone. The noble numbers here are V8 JIT on a 4+ GHz x86 core; on
  Hermes (no JIT, bytecode interpreter, BigInt math in software) the noble cases will be much slower.
  No on-device number exists yet: measure on the target phone before quoting any figure to a user.
- WebCrypto numbers are Node's OpenSSL (`process.versions.openssl`). Browsers differ (BoringSSL /
  NSS, other threading and scheduling); React Native has no WebCrypto at all, so the phone is noble.
- Calls are sequential (latency, one at a time). WebCrypto runs sign/verify on a thread pool, so
  concurrent requests on a server would scale beyond the single-call ops/s here; noble is single
  threaded JavaScript and would not.
- In-memory `fetch`: no network, no TLS, no parse of HTTP. The "real lists, warm" rows show the cost
  of the SDK's list path when cached, not of a real deployment.
- Fixed inputs (one credential, one 1% list): data-dependent costs (a different `x5c` size, a list
  that compresses better or worse) are not explored. A list with random 1% entries is close to the
  worst case for compression.
- A busy machine adds noise: compare "run spread" and the load average before trusting a difference of
  less than about 20%.
